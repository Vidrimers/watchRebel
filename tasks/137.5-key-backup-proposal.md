# 137.5 Key Backup — доработка таска

## Проблема текущей формулировки

Сейчас в таске:
> Шифрование приватного ключа паролем пользователя

Это создаёт проблему: если приватный ключ шифруется тем же паролем, что и вход в аккаунт, то смена пароля (например, через email-reset при "забыл пароль") сделает старый зашифрованный ключ нерасшифруемым — пользователь потеряет доступ к истории секретных чатов при обычной смене пароля. Это неожиданно и приводит к обращениям в поддержку.

## Предлагаемое решение: Recovery Phrase (отдельно от пароля аккаунта)

Разделить два независимых секрета:

- **Пароль аккаунта** — для входа в систему (может меняться когда угодно)
- **Recovery-фраза** — отдельный секрет только для E2EE, генерируется один раз, шифрует приватный ключ

**Главный эффект:** пользователь может сколько угодно менять пароль аккаунта — доступ к секретным чатам не теряется, потому что приватный ключ зашифрован не паролем, а отдельной фразой.

## Обновлённые подзадачи 137.5

- [x] 137.5.1 Генерация recovery-фразы ✅ 2025-07-26
  - 12 слов из BIP39-подобного словаря (2048 слов)
  - Генерируется при первом создании ключей
  - Показывается в RecoveryPhraseModal с чекбоксом подтверждения

- [x] 137.5.2 Шифрование приватного ключа recovery-фразой ✅ 2025-07-26
  - PBKDF2-SHA256 (100K итераций) → AES-256-GCM
  - Зашифрованный блоб + salt + iv загружается на сервер (таблица key_backups)
  - Сервер хранит только зашифрованный блоб

- [x] 137.5.3 UI подтверждения сохранения фразы ✅ 2025-07-26
  - RecoveryPhraseModal: сетка 12 слов, копировать, скачать .txt
  - Чекбокс "Я сохранил фразу" — блокирует "Продолжить"
  - Предупреждение: "мы не храним фразу"

- [x] 137.5.4 Восстановление ключа на новом устройстве ✅ 2025-07-26
  - KeyRecoveryModal: ввод фразы → restoreFromBackup()
  - GET /api/e2ee/backup → decryptPrivateKeyWithPhrase → localStorage
  - Приватный ключ не передаётся на сервер

- [x] 137.5.5 Разделение "смена пароля" и "доступ к E2EE" ✅ 2025-07-26
  - EmailConnectionBlock: "Смена пароля не влияет на доступ к секретным чатам"
  - Recovery-фраза независима от пароля аккаунта

## Итог

| Действие | Доступ к секретным чатам |
|---|---|
| Смена пароля аккаунта | Не теряется (ключ шифруется отдельной фразой) |
| Потеря пароля аккаунта (email-reset) | Не теряется |
| Потеря recovery-фразы | Теряется безвозвратно (это плата за честный E2EE) |
| Новое устройство + есть фраза | Восстанавливается локально |
| Новое устройство + нет фразы | История секретных чатов недоступна |

## Дополнения к остальным подзадачам таска 137

Введение recovery-фразы в 137.5 требует уточнений в соседних подзадачах, иначе останутся нестыковки.

### Уточнение к 137.1 (Генерация ключей при регистрации/логине)

- Текущая формулировка "приватный ключ хранится в localStorage" верна только для уже знакомого устройства.
- Нужно явно прописать сценарий **нового устройства**: localStorage пуст → клиент должен предложить ввод recovery-фразы для восстановления identity-ключа, а не считать, что ключа просто не существует, и генерировать новый (это создаст второй, несовместимый identity и сломает переписку).
- Добавить подзадачу: "137.1.1 Проверка наличия ключа на устройстве при логине: если ключа нет — предложить восстановление по recovery-фразе, и только при её отсутствии — сгенерировать новый ключ с явным предупреждением о потере старой истории."
- ✅ **137.1.1 реализовано** (2025-07-26): AppInitializer проверяет hasIdentityKey(), KeyRecoveryModal определяет сценарий (первый вход / новое устройство), восстановление по фразе — заглушка до 137.5.

### Уточнение к 137.6 (Key Rotation)

- Recovery-фраза (137.5) шифрует **identity-ключ** (X25519 private key, долгоживущий), а не сессионные ключи, которые ротируются.
- Нужно явно зафиксировать в таске: ротация сессионных ключей — отдельный процесс, backup/recovery их не затрагивает и не должен.
- Иначе при реализации может возникнуть путаница: разработчик попытается класть в recovery-бэкап актуальный сессионный ключ, что бессмысленно (он и так меняется).

### Новый пункт: поведение при отсутствии recovery-фразы

- Чекбокс подтверждения в 137.5.3 должен физически блокировать создание секретного чата, пока фраза не сохранена — но нужно продумать edge-case: что если пользователь закрыл вкладку/браузер во время показа модалки, до подтверждения?
- Предлагается: ключ и блоб на сервер не отправлять, пока чекбокс не подтверждён — то есть создание секретного чата с точки зрения сервера считается незавершённым до этого момента. Это исключает ситуацию "ключ создан, а бэкапа нет".

### Новый пункт: "Выйти со всех устройств" / logout everywhere

- В таске 137 сейчас нет сценария для функции "выйти со всех устройств" (актуально при подозрении на угон аккаунта).
- Нужно решить: инвалидирует ли эта функция локальные приватные ключи на удалённых устройствах, или только серверные сессии.
- Рекомендация: logout everywhere должен сбрасывать только серверные сессии (JWT/refresh-токены), но **не может** физически удалить приватный ключ с чужого устройства (сервер не имеет к нему доступа — в этом и суть E2EE). Это стоит прописать явно, чтобы не создавать у пользователя ложное ощущение, что "выйти со всех устройств" = "отозвать доступ к секретным чатам" — это невозможно технически без смены самого identity-ключа (что потребует пересоздания секретных чатов).

## 137.9 Верификация публичных ключей (Safety Number / защита от MITM)

**Контекст:** Публичные ключи пользователей (137.4) намеренно хранятся в открытом виде — это нормально для асимметричной криптографии. Но раз сервер является посредником при обмене публичными ключами, теоретически он (или тот, кто его скомпрометировал) может подменить публичный ключ одного из собеседников и провести MITM-атаку, оставаясь незаметным для обеих сторон переписки. Секретность самого приватного ключа тут ни при чём — проблема именно в доверии к каналу передачи публичного ключа.

**Подзадачи:**

- [ ] 137.9.1 Вычисление fingerprint / Safety Number
  - Вычисление короткого хеша (fingerprint) от связки публичных ключей обоих участников чата (по аналогии с Signal Safety Number / WhatsApp Security Code)
  - Отображение в UI секретного чата (например, в настройках чата или через иконку "проверить безопасность")

- [ ] 137.9.2 Сверка ключей между пользователями
  - Возможность сверить fingerprint вручную (сравнить цифры/слова с собеседником по другому каналу — голосом, лично)
  - Опционально: QR-код с fingerprint для сверки при личной встрече

- [ ] 137.9.3 Уведомление о смене публичного ключа собеседника
  - Если публичный ключ собеседника изменился (новое устройство без recovery, переустановка, потенциальная компрометация) — явное уведомление в чате: "Ключ безопасности собеседника изменился"
  - Не блокировать переписку автоматически (как в Signal), но требовать осознанного действия/подтверждения от пользователя перед продолжением в секретном чате

- [ ] 137.9.4 Логирование смены ключей (для аудита, не для сервера-расшифровки)
  - Хранение истории смены публичных ключей пользователя (только сам факт и таймстемп, не приватные данные) — чтобы клиент мог показать "ключ менялся N раз" как дополнительный сигнал для пользователя

**Примечание:** это отдельная задача от 137.8 (Тестирование и безопасность) — 137.8 проверяет, что реализация работает корректно и сервер не может расшифровать контент; 137.9 — про доверие к каналу обмена ключами, то есть защиту от активного MITM, а не пассивного чтения сервером.

## 137.10 UI-предупреждение к кнопке "Выйти со всех устройств"

**Контекст:** Кнопка "Выйти со всех устройств" находится в общих настройках аккаунта (вкладка "Аккаунт и безопасность") и не специфична для секретных чатов — она сбрасывает серверные сессии/токены. Но так как из 137.9 известно, что logout everywhere технически не может отозвать доступ к уже сохранённым секретным чатам на других устройствах (сервер не имеет доступа к приватным ключам), стоит явно предупредить об этом пользователя рядом с кнопкой, чтобы не создавать ложного ощущения полного контроля над данными.

**Подзадачи:**

- [ ] 137.10.1 Текст-пояснение рядом с кнопкой
  - Добавить короткую пометку под кнопкой/в тултипе: "Завершает активные сессии на всех устройствах. Не отзывает доступ к уже сохранённым секретным чатам на этих устройствах — для этого потребуется смена ключа безопасности."
  - Показывать пояснение только если у пользователя есть хотя бы один секретный чат (не показывать всем, чтобы не перегружать UI для тех, кто E2EE не использует)

- [ ] 137.10.2 (опционально) Отдельное действие "Отозвать доступ к секретным чатам"
  - Более радикальная опция, отдельная от обычного logout everywhere — генерация нового identity-ключа взамен старого
  - Требует явного предупреждения: старые секретные чаты станут недоступны для переписки (нужно будет заново обмениваться ключами с собеседниками), фактически "начать шифрование с чистого листа"
  - Актуально в первую очередь при подозрении на компрометацию устройства/аккаунта

- [ ] 137.10.3 Формулировка на этапе подтверждения (модалка при нажатии)
  - При клике на "Выйти со всех устройств" — в модалке подтверждения добавить ту же пометку про ограничение по секретным чатам, а не только в статичном тексте рядом с кнопкой (чтобы пользователь видел предупреждение в момент принятия решения, а не только заранее)
