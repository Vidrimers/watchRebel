# 138. Секретные групповые чаты с E2EE — дополнения

Таск 138 в целом логично наследует таск 137 (E2EE) и таск 126 (групповые чаты). Ниже — пять пунктов, которые стоит явно уточнить перед реализацией.

## 1. Механизм передачи группового ключа участникам

**Проблема:** в 138.2 написано "создание общего группового ключа шифрования", но не указано, как именно каждый участник его получает.

**Предложение:** групповой AES-ключ не должен пересылаться напрямую в открытом виде. Стандартный паттерн (как в Signal/WhatsApp):

- Групповой ключ генерируется один раз
- Для каждого участника ключ **оборачивается (wrap)** индивидуально — шифруется через ECDH с его публичным ключом
- В итоге на сервере хранится не один "общий ключ", а N отдельных зашифрованных копий (по числу участников), каждую может расшифровать только владелец соответствующего приватного ключа

**Куда добавить:** явно прописать в 138.1 (Backend — создание) и 138.2 (Backend — обмен ключами), чтобы при реализации не возник соблазн передать ключ проще и менее безопасно (например, зашифровав его один раз общим паролем группы).

**✅ Реализовано:** групповой ключ шифруется индивидуально для каждого участника через ECDH. На сервере N зашифрованных копий в таблице `group_keys`.

## 2. Ротация ключа не отзывает уже прочитанные сообщения

**Проблема:** в 138.4 сказано "при удалении участника — ротация группового ключа", но не уточняется, что это защищает.

**Пояснение:** ротация защищает только **будущие** сообщения после удаления участника. Если его клиент уже расшифровал и локально закешировал историю до этого момента — эти сообщения остаются на его устройстве, ротация ключа их не отбирает. Это ожидаемое поведение E2EE-систем (так работает везде — Signal, WhatsApp), а не баг.

**Куда добавить:** явное пояснение в 138.4, чтобы не создавать у пользователей ложных ожиданий вида "удалил из чата — и он больше ничего не видит из истории".

## 3. Передача прав создателя при его уходе

**Проблема:** в 138.4 указано "только создатель может добавлять участников" — но не описан сценарий, если создатель покинул группу или удалил аккаунт.

**Решение (Вариант Б):** при уходе создателя права автоматически переходят к следующему участнику:
- Приоритет 1: назначенный админ (если есть)
- Приоритет 2: первый по порядку вступления (после создателя)
- Группа продолжает функционировать, новые участники могут добавляться
- Уведомление в чате: "Права создателя переданы пользователю X"

## 4. Восстановление групповых ключей через recovery-фразу (связь с 137.5)

**Проблема:** recovery-фраза из 137.5 шифрует и восстанавливает **identity-ключ** пользователя. Групповые (сессионные) ключи — отдельная сущность, и если они хранятся только в localStorage конкретного устройства, при восстановлении identity-ключа на новом устройстве пользователь получит доступ к секретным **личным** чатам, но не факт, что получит доступ к секретным **группам**.

**Что нужно решить явно:**
- Вариант А: групповые ключи также бэкапятся — шифруются identity-ключом пользователя (аналогично personal secret chats) и хранятся на сервере в зашифрованном виде для восстановления
- Вариант Б: при восстановлении на новом устройстве клиент запрашивает повторный обмен ключом у оставшихся участников группы (аналог "новый участник не видит старые сообщения", но применительно к своему же аккаунту на новом устройстве)

**Рекомендация:** выбрать Вариант А для консистентности с 137.5 — иначе пользователь, потерявший устройство и восстановившийся по recovery-фразе, будет удивлён, почему личные секретные чаты восстановились, а секретные группы — нет.

## 5. Верификация ключей участников группы (связь с 137.9)

**Проблема:** в 137.9 предложена верификация публичных ключей (Safety Number) для защиты от MITM при подмене ключа сервером — этот риск актуален и для групп, только теперь умножен на число участников.

**Предложение:** расширить 137.9 (или добавить отдельный пункт в 138) на групповой случай:
- Уведомление, если публичный ключ **любого** участника группы изменился (не только при 1-к-1)
- В UI группы — возможность посмотреть список участников с индикатором "ключ проверен / ключ недавно менялся"

**Куда добавить:** либо как расширение существующей 137.9, либо как отдельный пункт 138.9 "Верификация ключей участников группы" — в зависимости от того, удобнее ли вести это как общую фичу для 137+138 или отдельно для групп.
